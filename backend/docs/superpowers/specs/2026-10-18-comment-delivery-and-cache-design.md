# 评论消息可靠投递与缓存正确性设计

> 2026-10-18 审阅结论：发件箱方向可用，原稿关于完整消费者幂等和 top 500 重建的承诺不成立。下面补充逐事件持久状态、正文稳定键、消费确认和缓存完整性要求；不能只实现发送端发件箱就宣布全链路可靠。

## 背景

评论发布目前通过 RocketMQ 异步投递。发送端重试耗尽后只记录日志，没有持久补偿；因此 broker 连续不可用或发送进程退出时，评论消息可能永久丢失。评论列表 Caffeine 批量加载器会给缺失项放入空字符串，造成负缓存；Redis MGET 局部缺失时还存在 ID 与结果位置错配风险。热门评论 Lua 脚本在 500 条满缓存下更新已有成员会先剔除最低分成员，且以字符串比较分数。

## 目标

- 使用持久化发件箱代替“发送失败后才落库”的脆弱兜底，保证已被接口确认受理的评论有可恢复的发送记录。
- 允许至少一次投递；通过稳定的评论 ID 与消费者幂等写入避免重复评论。
- 评论列表的本地缓存、Redis 缓存缺失时能可靠回源，不把缺失伪装成有效空内容。
- 热门评论缓存基数始终不超过 500，更新已有评论不降低缓存基数，分数按数值排序。

## 发件箱方案

### 数据记录

在 MySQL 增加评论消息发件箱记录，包含唯一消息键（使用评论 ID 或其稳定派生键）、topic、payload、发送状态、已尝试次数、下次可重试时间、最近错误摘要、创建/更新时间及租约字段。唯一键确保同一已受理事件重投不会建立多个任务；现有 HTTP 请求每次生成新 commentId，因此本轮不能据此承诺客户端请求重试幂等。Payload 含评论正文，日志不得打印完整 payload；数据库访问沿用现有权限边界。

记录写入需要与评论发布受理动作放在一个 MySQL 本地事务中。当前接口没有先持久化评论元数据，因此以发件箱行作为“已受理”的持久记录；接口只有在该行已提交后才能返回已受理。调度器以有限批次租用到期记录，状态为 PENDING → SENDING → SENT；租约包含 owner/version，结果更新必须检查租约身份，过期租约可重新领取。SENT 只代表 broker 接收，不代表评论已保存。

如果目标仍是“已受理评论最终入库”，还必须有 APPLIED 记录或等价的消费者持久状态、待处理巡检及 DLQ 重驱；消费失败不会自动把发布端 SENT 改回 PENDING。首次启动无位点的新消费组需要明确从首条待处理消息/指定时间消费，不能沿用从最后位点启动而跳过已入队事件。

### 投递和消费者

- 允许消息发送成功但进程在标记完成前退出。消费者必须按事件类型和 commentId 持久去重，且该记录独立于可被物理删除的评论行；否则删除后重放会重新插入已删评论。去重记录保留期覆盖发件箱和 broker 的可重放生命周期。
- contentUuid 在发件箱 payload 中一次生成并固定，重投复用；当前消费者每次重新随机生成 UUID 的行为必须修改，已有元数据复用其已存 UUID。稳定 commentId 本身不能保证 Cassandra 正文主键稳定。
- 评论元数据事务内同时持久化逐评论的计数/缓存后续事件，再独立投递；不能以整批 `insertedRows > 0` 为整批所有评论发送增量，也不能在事务提交后仅依赖一次异步发送。
- 笔记评论数、子评论数等增量消费者须按事件 ID 去重，并将去重与 MySQL 增量放在同一事务；Redis 失效/重建或更新也需可恢复。不得在仅入进程内 BufferTrigger 后就确认 broker 消费成功；可以先持久化 inbox 再聚合。
- 不在达到任意次数后静默删除/丢弃发件箱记录；持续失败记录保留并继续以封顶退避周期重试，同时有错误日志和可查询状态。
- 初次发送、发送超时、服务重启和多个发送器竞争通过发件箱状态转换处理；消费毒消息通过持久消费状态、DLQ 巡检和重驱处理。
- 原来 `SendMqRetryHelper` 的重试可保留为短时快速重试；最终成功/失败结果都回写发件箱。持久化机制不能依赖该进程内线程池存活。

### 一致性边界

发件箱事务只能保证 MySQL 内“业务受理记录 + 待投递事件”同时提交，不能把 MySQL、RocketMQ 和 Cassandra 变成一个分布式事务。消费确认边界至少包括元数据、正文和后续持久事件完成；KV 失败不得确认成功。`INSERT IGNORE` 只防止同时存在重复主键行，不能替代正文、后续计数、删除墓碑和 APPLIED 状态的幂等协议。

## 评论详情缓存

- Caffeine 的 `getAll` 加载器只返回有效命中，不为缺失 ID 写入 `Strings.EMPTY` 占位；缺失项保持未缓存，后续请求可以重新查 Redis/数据库。
- 将每一个缺失的本地 key 与 Redis MGET 的 key 列表一一绑定，按同一缺失子集索引处理返回值，不得用完整评论 ID 列表去索引部分 MGET 结果。
- Redis 未命中项按实际 ID 集合回源 MySQL；回源成功后才填充 Redis 与 Caffeine。数据库不存在的已删评论不缓存成空字符串，必要的负缓存应有明确、短 TTL 且不影响评论列表返回。
- `is_content_empty=false` 时必须成功加载该评论 UUID 的正文；KV 失败或正文未就绪不得写入长 TTL 详情缓存。合法图片评论的无正文标记仍可缓存。
- 有效评论按 ZSet 返回的 ID 序列从 map 组装，删除最后用详情缓存旧 heat 再排序的行为。

## 热门评论 ZSet

- 更新 Lua 以 `tonumber()` 比较评分，单次 Redis 变更原子完成。先校验全部参数的成对数量、数值和重复 member 处理规则，避免执行到一半报错后保留部分已写内容。
- 已存在成员先更新分数，不先淘汰其他成员；对新增成员按当前最小分数判断是否可进入 top 500。
- 更新后执行一致的裁剪逻辑，缓存最多 500 项；满 500 项更新已有成员时条数保持 500。只有 500 条缓存不能判断第 501 条候选，因此热度下降（包含降为 0）时先使该笔记热榜失效，查询回退 SQL，再重建；热度消费者不得过滤掉 0 分变更。
- SQL 重建结果在临时 key 中生成，以代数/版本条件原子替换并设置 TTL；并发热度更新推进版本并再次失效，旧快照不得覆盖新版本。禁止直接复用当前逐条 pipeline ZADD 的回填函数，因它不清旧成员且不裁剪。空结果也要有明确短期空榜标记。
- 对 9.99 / 10.00、相同分数、满 499 / 500 / 501 条、重复 member 和分数下降分别验证。
- 排序明确为 `heat DESC, commentId DESC`；SQL、ZSet 成员编码、同分准入和最终组装保持一致。Redis 成员使用 19 位左补零的非负 Long 十进制 ID 字符串以匹配数值次序，禁止把完整 Long 转 Lua number 做次级比较。现有 SQL 只有 heat 排序，不能称为已有稳定并列规则。

## 不在本次范围内

- 不重写评论 API、评论层级模型和计数业务口径。
- 不把 RocketMQ 交付改为同步写 Cassandra 后再返回；发件箱保证已受理消息可恢复，评论列表仍遵循异步消费与最终一致。
- 不全量清空 Redis/Caffeine，也不删除历史评论数据。

## 验收场景

- 随机评论在 broker 暂不可用时被持久化；恢复 broker 后最终进入 MySQL 和 Cassandra，重启发送服务后仍可投递。
- 模拟 broker 已接收但发送端未标记成功的重复发送，结果只有一条评论元数据且正文正确。
- 验证“重复 A + 新 B”混批只计 B、元数据提交后发送后续消息前崩溃仍可恢复、已删评论重放不复活、KV 重试不产生新 UUID、消费者缓冲期退出不丢已确认增量；首次消费组和 DLQ 恢复路径也需实测。
- 模拟本地缓存空/部分命中、Redis 多个键中一个缺失、数据库回源和删除评论，返回 ID/正文正确且后续请求不被空占位影响。
- ZSet 达到 500 条后反复更新已有评论仍为 500；评分 10.00 高于 9.99；新增低分评论不挤出 top 500。
- 验证热度降为 0、501 号候选补入、SQL 快照与并发热度更新、同分跨页、合法无正文和暂缺正文缓存边界。
- 用随机实体验证后清理数据库、Redis 和 Cassandra 测试数据；编译并启动 comment、kv 相关服务执行接口验证。

## 风险与运维

- 发件箱需要保留策略，但只能在消息成功完成且达到审计保留期后归档/清理；清理必须分批、可观测，不能用无条件全表删除。
- 长期失败会占用发件箱空间；需暴露待发送数量、最老消息年龄和持续失败日志，并在本地部署文档说明排查方法。
- 发送器的锁租约超时可能造成重复消息，消费者幂等是强制要求而非优化项。

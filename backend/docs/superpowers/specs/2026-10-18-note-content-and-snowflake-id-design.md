# 笔记正文可用性与大 ID 点赞收藏设计

> 2026-10-18 审阅结论：同步正文与禁止缓存不完整详情的方向可用；原稿“重复发布 upsert 幂等”“任意 SQL 异常即可删除正文”“支持旧新版滚动写”等表述不成立，已修订。Set 只解决完整 ID 表示，不据此承诺已修复既有异步关系消息的所有竞态。

## 背景

带正文笔记目前通过 RocketMQ 事务消息先提交 MySQL 元数据，再由 KV 消费者异步写入 Cassandra。发布成功后正文可能暂时不可读；详情服务会把正文 `null` 的结果当成成功详情写入 Redis 和 Caffeine，导致后续缓存持续返回空正文。另一个问题是点赞、收藏 Roaring Lua 脚本把 Snowflake `Long` 笔记 ID 当作位图 offset，而 Redis Roaring bitmap 的位置范围只有 32 位。

## 目标

- 发布接口确认成功时，笔记正文已能从 KV 服务读取。
- 正文暂不可用时，详情查询返回可重试结果，不把缺失正文写入 Redis 或 Caffeine。
- 保持合法无正文笔记的既有行为。
- 点赞与收藏精确支持完整 Snowflake Long ID，不发生截断、溢出或错误命中。
- 不改变公开请求/响应字段和关系状态的 MySQL 权威来源。

## 正文发布流程

### 带正文笔记

1. 继续使用现有 RocketMQ 事务消息作为发布流程入口。
2. 本地事务监听器在 MySQL 插入笔记元数据前，同步调用 KV Feign 将正文按 `contentUuid` 写入 Cassandra。
3. 只有 KV 写入成功且 MySQL 元数据明确提交，监听器才返回 COMMIT。RocketMQ 的 ROLLBACK 状态不会自动回滚 Cassandra 或已提交的 SQL。
4. 区分确定未提交和提交结果未知。只有确定 MySQL 未提交时，才可补偿删除孤立正文；SQL 响应超时或连接中断时先按 noteId + contentUuid 查证。仍无法确定时保留正文并返回 UNKNOWN/可重试结果，禁止直接删除可能被有效元数据引用的正文。补偿失败记录 ID 与 UUID 并允许排查。
5. 新发布链路的 `SaveNoteContentConsumer` 不再 upsert 正文，可只确认或处理不写正文的通知。编辑沿用 contentUuid，原发布消息延迟重放会把新正文覆盖回旧内容，清空正文后也可重建已删 KV；`IF NOT EXISTS` 同样不能保证清空后不复建。升级前停写并处理完旧发布消息，避免旧消费者继续改正文。
6. 发布服务只有收到明确 COMMIT 状态才返回成功；ROLLBACK/UNKNOWN 按当前 API 错误模型返回失败或可重试错误，不得无条件返回成功。

事务回查明确区分已提交、确定失败、仍在执行与查询失败。同步 KV 增大了 SQL 插入前的窗口，不能把“暂时查不到行”立即解释为 ROLLBACK；仍在执行/查询失败应为 UNKNOWN。实施计划要列出 KV、SQL、整个回调及 broker 回查的超时预算，确认元数据提交后通知发送失败不改变发布结果。

空正文笔记保持现有直接入库路径，不调用 KV，也不要求正文存在。

### 详情查询及缓存

- 当 `is_content_empty=false` 且 KV 未返回非空正文时，详情不能作为成功结果缓存；返回可重试的正文处理中/暂不可用业务错误。
- 对 `is_content_empty=true` 的笔记，空正文是合法结果，可沿用现有缓存行为。
- 仅在必要正文已成功加载后，才写 Redis 详情缓存和 Caffeine 本地缓存。
- 更换详情缓存 key 版本/命名空间，使之前可能缓存的空正文不再被读取；新旧缓存按 TTL 自然过期，不全量扫描或删除旧 key。
- 内部缓存包装携带 `contentRequired`（或等价的 `isContentEmpty`），公开响应仍返回原 VO；当前 VO 没有此字段，单看空 `content` 无法区分合法无正文和丢失正文。缓存命中依据内部标记验证，历史无标记对象回源。

## 点赞/收藏 ID 表示

- 不再把 `noteId` 当作 bitmap bit offset。
- 为点赞状态与收藏状态各使用 Redis Set 存储十进制完整 ID 字符串，分别采用新的版本化 key 前缀和 `SISMEMBER` / `SADD` / `SREM` 语义。
- 版本化 key 避免同一 Redis key 先后存放 Roaring 与 Set 类型产生 WRONGTYPE；历史 bitmap key 不在切换时批量删除。
- 成员使用 `Long.toString` 和显式字符串序列化，所有写入/查询脚本保持一致；不能在 JSON 序列化模板下混用数字与带引号字符串。Set 为空时需要独立 ready 标记或保留的非 ID sentinel，最后一个 SREM 不应让已初始化空集误判为从未装载。
- 新 key 缺失时可从关系表回源，但数据库异步消费期间可能落后；不得声称一次 SADD 合并能修复取消竞态，也不得用“key 存在”把单次新增形成的局部集合作为完整快照。冷初始化与新写入的版本/待处理变更协议需单独验证，未完成前把这项列为既存最终一致性边界。
- 当前点赞/收藏消息发送失败仅日志、消费者部分批次按奇偶折叠，属于既存关系交付问题。本项只承诺 ID 不截断/不串号，不能把这些问题写成已随 Set 自动解决。
- 本方案用更多 Redis 内存换取完整 Long ID 支持与实现简单。若测试数据量明显增长，再基于实测决定是否使用分段位图；本次不自行新增复杂编码。

## 兼容和部署

- 新版应用发布前后，数据库关系表继续作为最终权威；切换缓存版本后首次读取可从数据库重建。
- 缓存切换采用维护窗口：暂停相关写入口，等待旧发布及点赞/收藏消息处理完毕，停旧 note/kv 实例，部署单一新版本及新缓存前缀后恢复写入。此方案不支持旧新版并行写的滚动发布。
- 统计 Redis 内存和 Set 大小，并在本地环境用远大于 `2^32` 的随机 Snowflake ID 验证。

## 不在本次范围内

- 不修改 Snowflake 生成算法或数据库 ID 列类型。
- 不改笔记点赞、收藏接口的鉴权和关系表语义。
- 不将所有 Roaring 用途从项目移除；仅处理直接使用笔记 ID 作为 offset 的点赞/收藏路径。

## 验收场景

- 带正文发布成功后立刻读取详情，正文与发布内容一致；KV 不可用时发布不能返回成功。
- 模拟 KV 成功、MySQL 确定未提交，验证补偿删除及失败日志；另模拟 SQL 超时或提交结果未知，验证不删除正文、返回 UNKNOWN 并执行回查。
- 正文暂缺时重复读取均不产生空正文缓存；正文变为可用后下一次读取返回正文。
- 无正文笔记详情仍可正常展示和缓存。
- 选用 `> 2^32` 的随机 Snowflake ID 分别测试点赞、取消点赞、收藏、取消收藏和状态查询；验证数据库关系与接口结果一致。
- 增加同低 32 位、不同高位的两个 ID，`2^32` 边界，以及 `2^53` 以上相邻 ID；验证精确字符串、空集合和批查原始顺序。关系表对比等待消费者追平，初始化竞态单列结果，不能用普通 ID 测试代替。
- 编译并启动 note、kv 服务执行端到端验证；随机测试数据和专属缓存键在验证后清理。

## 风险与取舍

- 在 RocketMQ 本地事务回调中同步调用 KV 会增加事务耗时，并使 KV 可用性参与发布可用性。此为获得“发布成功即正文可读”的明确取舍，必须设置 RPC 超时并验证 RocketMQ 事务回查和异常行为。
- MySQL 与 Cassandra 没有共同事务；补偿只能减小孤儿数据，不能提供数学意义上的跨库原子提交。后续如需更强可靠性，应设计持久化 saga/outbox 和正文状态机，不在本轮扩大为重构整个发布协议。
- Redis Set 相对压缩 Roaring 占用更多内存，实施需报告实测容量影响。
- 另一可选修法是在 Java 将 Long 拆为高 32 位 key 分段与低 32 位 bitmap offset，以保留教程 Roaring；但本仓库 Snowflake 高段约每秒变化，可能形成大量稀疏 key，不能直接断言更省内存。原稿 Set 选择可保留，作为可维护性取舍明确记录。

# 计数对账与搜索索引一致性设计

> 2026-10-18 审阅结论：原稿不能直接用于在线自动回写。本文已修正实体类型和业务口径；在线校准与增量消息的水位协议仍是实施前置条件。详细证据见同目录 `2026-10-18-reliability-design-review.md`。

## 背景

当前项目已有 `FollowingCountShardingXxlJob` 和 `NoteLikeCountShardingXxlJob`，但 19.13 教程列出的另外五项对账作业未完成。搜索服务可以按 ID 重建笔记和用户文档，但现有 Canal 监听主要覆盖 `t_note`、`t_user`，计数表变化没有完整进入索引刷新链路。

项目有七类日增量标记表。夜间对账应只重算发生变化的实体，不对全库做周期性 COUNT 扫描。当前标记消费者会吞掉 SQL 失败，并且用 Bloom 阳性跳过持久化，因此这些表还不是完整可靠的变更清单；需要先修复标记写入和上游事件交付，不能据此承诺所有漂移都能被发现。评论数及评论点赞等不在这七张日增量表覆盖范围内，本轮不自动把它们加入周期校准。

## 目标

- 补齐五种缺失的分片广播计数对账：粉丝、笔记收藏、作者获赞、作者获收藏、作者发布笔记数。
- 每种计数只重算对应日增量表中的实体，分批执行。自动回写的前提是与在线增量消费有明确版本/水位协调；缺少该协议时，只能运行比对审计，或在停写且相关 MQ 已处理完毕的维护窗口回写。
- MySQL 中的计数值是对账结果；已存在的 Redis 计数 Hash 在更新成功后同步更新，不为无缓存的实体强行创建缓存。
- 确保用户资料计数和笔记计数变更能最终更新 ES 用户与笔记文档。
- 对失败提供可重试信号，保留尚未完成的日增量记录。覆盖式重跑只能说明作业自身不累加，不能防止迟到 MQ 再次累加或覆盖并发增量。

## 五项指标与来源

| 对账结果 | 日增量表 | 权威来源 | 计数表字段 |
| --- | --- | --- | --- |
| 用户粉丝数 | `t_data_align_fans_count_temp_日期_分片` | `t_following` 中目标用户的有效关系数 | `t_user_count.fans_total` |
| 笔记收藏数 | `t_data_align_note_collect_count_temp_日期_分片` | `t_note_collection` 中该笔记 `status=1` 的关系数 | `t_note_count.collect_total` |
| 作者获赞数 | `t_data_align_user_like_count_temp_日期_分片` | 作者全部笔记所获 `status=1` 的 `t_note_like` 关系数之和，包含软删除笔记以保持现有在线口径 | `t_user_count.like_total` |
| 作者获收藏数 | `t_data_align_user_collect_count_temp_日期_分片` | 作者全部笔记所获 `status=1` 的 `t_note_collection` 关系数之和，包含软删除笔记以保持现有在线口径 | `t_user_count.collect_total` |
| 作者发布笔记数 | `t_data_align_note_publish_count_temp_日期_分片` | `t_note` 中该作者未软删除的笔记数 | `t_user_count.note_total` |

作者获赞、获收藏、发布数三张增量表在运行代码中都使用 `user_id`，直接标记受影响的作者。`database/19.1-data-align-daily-tables.sql` 的发布数示例误写为 `note_id`，须与 `CreateTableMapper.xml`、`InsertMapper.xml` 统一；对现有表先检查结构，禁止直接删表重建。

发布笔记数排除软删除笔记，保留其他状态。作者获赞/收藏则保持当前在线口径：笔记软删除只减少发布数，不自动减少作者历史获赞/收藏。若未来改变这两个指标口径，必须同时修改在线事件以及删除/恢复动作的增量标记。

## 处理流程

1. 显式枚举物理表分片，以 `physicalIndex % executorShardTotal == executorShardIndex` 分配给 XXL 执行器；不能将执行器序号直接当作物理表序号。单执行器也必须覆盖当前三个物理分片。识别并继续处理仍有积压记录的较早日期分片，避免失败记录留在旧表后永远无人重试。
2. 从关系表或笔记表按业务状态重新计算真实计数，而不是消费增量值做加减。
3. 校验回写前提后才覆盖相应计数表；计数行不存在时使用 upsert。安全的最小实现是比对审计默认开启、维护窗口修复；若要不停写自动修复，需先设计源事件版本、已消费水位及迟到事件处理，单独给 Job 加锁不够。
4. 仅当 Redis 对应 Hash 已存在时，用 Lua 原子执行 EXISTS 与 HSET，保留原 TTL，防止检查后过期再 HSET 创建残缺、无过期时间的 Hash。缓存回填也须服从同一版本边界。
5. 让计数变化通过数据库 binlog/Canal 事件刷新 ES。现有 Job 的直接重建请求和用户资料触发的笔记重建必须进入同一有序刷新入口；不能让旧查询的覆盖写晚于新结果。
6. 当前批次数据库和缓存操作成功后，才物理删除对应增量标记；失败批次保留标记供下次运行。临时表清理任务只能清理已完成且为空的分片表，不能按日期无条件删表。

标记消费者使用 SQL 唯一键及 `INSERT IGNORE` 去重，真实 SQL 失败必须传播以触发重试；Bloom 只能作辅助，不能据阳性结果跳过必要标记。源记录持久化与消息发送之间的丢失窗口也须通过源事务 outbox 或对应 binlog 方案覆盖。未补齐这些前提时，对账是尽力审计，不能称为完整兜底。

## 搜索索引同步

- 同时扩展 Canal 客户端订阅配置、部署覆盖配置和事件处理分支，加入 `t_note_count`、`t_user_count`；仅修改服务端 filter 或 switch 不能收到当前客户端未订阅的表。
- `t_note_count` 事件提取 `note_id`，调用已有笔记文档重建 RPC；`t_user_count` 事件提取 `user_id`，调用已有用户文档重建 RPC。
- 文档重建从 MySQL 重新读取完整当前文档，避免把单个字段的 binlog 部分更新误用于 ES。
- 主体不存在或不符合索引条件时，明确删除相应 ES 文档；当前空查询 no-op 和物理 DELETE 仅日志不能直接沿用。
- 现有重建 RPC 会捕获 ES 异常后返回成功，资料更新 bulk 未检查单项失败；实施必须修正失败契约、检查 Feign 业务响应与每个 bulk item，让异常传播到 Canal rollback，成功后才 ack。
- 多入口全量覆盖写须具备同实体串行刷新或明确源版本保护；重复幂等不能保证旧查询晚写不覆盖新资料/新计数。此顺序协议在实施计划中确定后再批准在线链路。

## 不在本次范围内

- 不新增全表定期校准，不扫描全量用户、笔记或关系表。
- 不把评论数、子评论数、评论点赞数加入日增量对账，除非后续确认它们有完整且可靠的受影响实体标记表。
- 不改变接口返回字段、搜索排序规则或现有计数事件的业务含义。
- 不引入新的搜索引擎或替换 Canal。

## 验收场景

- 对每一项五种指标分别准备随机测试实体，创建并取消对应关系/笔记状态后，执行对应分片任务，核对 MySQL 结果与源关系表 COUNT 一致；重复执行结果不变。
- 失败注入时，未完成的增量标记保留；成功处理的标记可被清理。
- 验证单执行器处理全部三个物理分片、扩缩容后不漏表；SQL 标记失败和 Bloom 假阳性均不能永久漏记。
- 构造源关系已提交但计数 MQ 迟到，以及 COUNT 后在线增量到达的场景；未定义水位协议前，修复模式应拒绝在线覆盖写。
- 验证缓存存在时字段更新、缓存不存在时不产生不必要的 Hash。
- 更新 `t_note_count` 后读取 ES 笔记文档；更新 `t_user_count` 后读取 ES 用户文档，确认计数最终一致。
- 验证 ES bulk 单项失败会重试、主体删除会移除文档、旧资料查询晚写不能覆盖新计数/昵称。
- 使用随机数据并在验证完成后清理；服务实测包括启动 data-align、search 及 Canal 相关链路。

## 风险与取舍

- 作者级获赞/收藏需要在变更用户的所有笔记上聚合，SQL 必须利用现有索引并按用户 ID 批量处理；若查询计划显示全表扫描，应调整 SQL/批次，而不是改为全库周期校准。
- Canal 会带来异步索引延迟；MySQL 是计数对账权威值，ES 是最终一致的查询副本。
- 当源表状态过滤口径与历史教程数据不一致时，需以本仓库已有业务枚举及接口口径为准，并在实现提交中记录明确差异。

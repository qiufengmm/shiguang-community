## 职责

搜索服务对外提供两类查询：

- 关键词搜笔记：输入关键词（如「壁纸」），按相关性返回笔记，热门的优先
- 关键词搜用户：输入关键词，返回相关用户

两类查询都支持条件筛选：排序规则、笔记类型、发布时间等。

## 搜索引擎选型

选用 Elasticsearch，理由：倒排索引带来的高性能、可水平扩展（分片与副本保证高可用）、查询 DSL 丰富、具备实时聚合分析能力、客户端生态完善。

## 增量同步方案

| 对比维度 | MQ 通知方式 | Canal |
| --- | --- | --- |
| 实时性 | 较高，受 MQ 消费速率影响 | 极高，几乎实时 |
| 一致性 | 需事务消息或补偿机制 | 与数据库一致性强 |
| 数据来源 | 支持多数据源 | 仅限数据库 |
| 开发复杂度 | 需开发 MQ 生产与消费逻辑 | 需开发 binlog 解析与处理逻辑 |
| 运维复杂度 | MQ 需高可用部署 | Canal 部署运维成本较高 |
| 适用场景 | 多数据源、复杂逻辑 | 单一数据源、简单逻辑 |

Canal 的原理是伪装成 MySQL 从库读取 binlog，优点是对业务零侵入、与数据库强一致、实时性高；缺点是运维成本高、只能捕获库表变更、需要额外把原始变更加工成 ES 文档格式。

**选型结论：采用 Canal** 做笔记、用户的实时增量索引同步（第 22 章实现），全量与增量初始化使用 logstash-input-jdbc（20.10、20.11）。

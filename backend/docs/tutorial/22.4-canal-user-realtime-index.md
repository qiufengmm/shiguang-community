# 22.4 自定义 Canal 消费：用户实时增量 ES 索引

- 扩展 `SelectMapper.selectEsNoteIndexData`，允许按 `userId` 查询用户发布的公开、正常笔记；新增 `selectEsUserIndexData`，查询启用且未逻辑删除的用户及笔记数、粉丝数。
- `CanalSchedule` 处理 `t_user` INSERT：查询用户全量数据并写入 `user` 索引；处理普通 UPDATE：通过 Bulk API 覆盖用户和其全部公开笔记索引；用户禁用或逻辑删除时只删除用户文档，保留已发布笔记。
- 验证：JDK 17 下搜索服务 `package` 成功并运行于 8092。用随机测试用户和两篇测试笔记验证了用户 INSERT 建索引、昵称 UPDATE 同时更新用户和两篇笔记、`status=1` 只删除用户文档、恢复后重新建索引、`is_deleted=1` 再次只删除用户文档。每个删除分支后，两篇公开笔记仍在 ES。`/search/ext/dict` 返回 HTTP 200，Canal 消费错误数为 0。
- 已清理测试用户、笔记、计数表记录及对应 ES 文档，并确认 MySQL 测试行数为 0、ES 测试文档为 404。
- **必要偏离：**实测发现 22.3 的 Canal 消费器对 DELETE 事件也读取 `afterColumns`，而 Canal 将删除行主键放在 `beforeColumns`，导致消费者反复回滚同一批次并报空指针。为让积压批次继续消费，本节把 DELETE 事件改为读取 `beforeColumns`。这是 22.4 外的最小兼容修复。
- **教程边界：**教程只覆盖用户 INSERT/UPDATE 和笔记逻辑隐藏、下架等事件。笔记物理 DELETE 仍记录为未处理事件，不会自动删除 ES 文档；本次为清理测试数据，按精确 ID 手动删除了对应文档。若业务允许物理删除，后续应补充删除事件索引清理。
- **遗留风险：**笔记查询 SQL 输出 `img_uris`、`nickname`、`avatar`，而现有笔记索引代码使用 `cover`、`creator_nickname`、`creator_avatar`；按教程保留，字段不一致风险同 22.3。当前 Canal 日志还会记录完整用户列，其中包含密码哈希和手机号，部署生产环境前应过滤敏感字段。

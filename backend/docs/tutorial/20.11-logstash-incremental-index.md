# 20.11 增量 ES 索引：Logstash JDBC

## 笔记增量

`sync-es-note-index` 使用 `update_time` 作为时间戳跟踪列。SQL 在公开且正常展示的笔记中筛选笔记或作者更新时间超过 `:sql_last_value` 的记录，写入 `note` 索引时仍用笔记 ID 作为文档 ID。

JDBC 配置加入 `jdbc_default_timezone=Asia/Shanghai`、`use_column_value=true`、`tracking_column=update_time`、`tracking_column_type=timestamp`、`clean_run=false`，状态保存到本机 Logstash 配置目录下的 `sync-es-note-index/last_run_time`。

## 用户增量（教程小作业）

`sync-es-user-index` 以 `u.update_time` 为跟踪列，选出启用且未删除、更新时间超过 `:sql_last_value` 的用户，写入 `user` 索引时仍使用用户 ID 作为文档 ID。查询额外返回格式化的 `update_time` 字段。其检查点保存在独立的 `sync-es-user-index/last_run_time` 文件，避免两个 JDBC 输入共用游标。参见 [Logstash JDBC input 文档](https://www.elastic.co/docs/reference/logstash/plugins/plugins-inputs-jdbc) 中的状态文件说明。

两个状态文件位于 `E:\java_workspace\logstash-7.3.0\config\mysql\` 下的各自管道目录；它们是运行时数据，不纳入 Git。

## 验证记录

- 运行环境：Logstash 7.3.0、`logstash-input-jdbc` 4.3.13、JDK 8、Docker MySQL 与 Elasticsearch。
- 两份配置分别通过 `logstash.bat --config.test_and_exit -f <jdbc.conf>`，都输出 `Configuration OK`。
- 笔记首次查询后，修改一条笔记的时间戳，下一轮 JDBC 查询返回 1 条，ES 文档随之更新。
- 用户首次查询返回 2 条；修改一名有效用户的时间戳后，下一轮增量查询返回 1 条，ES 文档随之更新。
- 验证使用随机秒数构造临时更新时间；随后将两条 MySQL 时间、完整 ES 文档和两个 `last_run_time` 检查点还原。验证前后源表有效记录数均为 3 篇笔记、2 名用户，ES 索引文档数也分别为 3、2。两个 Logstash 进程均已停止。

## 按教程保留的时区与游标风险

Docker MySQL 会话时区为 `SYSTEM`，其时钟与本机 Logstash 的上海时区相差 8 小时。实测中，笔记检查点是 UTC 时间；更新时间只比原始检查点大十几秒时，JDBC 查询返回 0 条。将临时更新时间设到检查点换算后再增加随机秒数，查询返回 1 条。教程也提醒 SQL 起始时间会出现 8 小时偏移。后续使用时应关注 MySQL 时间值、JDBC 检查点和 `jdbc_default_timezone` 的换算；本节保留教程设置，没有私自改动时区方案。

教程笔记 SQL 以 `n.update_time` 作为返回的 `update_time` 跟踪列，同时用 `u.update_time` 的 OR 条件捕获作者资料变更。这可能导致作者的更新时间晚于该笔记更新时间时，同一篇笔记在游标越过作者更新时间前被重复捞取。按教程保留该 SQL，后续如调整需单独验证游标语义。

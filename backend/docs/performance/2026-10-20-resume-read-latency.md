# 2026-10-20 简历读接口耗时实测

## 目的与环境

为实习简历提供可解释、可复核的关注列表耗时与笔记详情缓存收益。正式 RunId 为 `20261020-formal2`，业务源码提交为 `f4648e616fe6fd698726e03e8e435dc27d4e9073`。

- 使用已有本地 Docker Linux 服务：4 vCPU、8328429568 字节内存，Docker Server 29.5.3。宿主机为 Windows，物理内存约 15.8 GiB。
- 应用为 JDK 17，Compose 默认 Java 堆上限 192 MiB、应用容器内存上限 420 MiB，`ActiveProcessorCount=2`。各容器镜像 ID、启动时间和资源快照保留在运行目录。
- 客户端为现有 frontend 容器内 curl 8.12.1，直连内部 note/user-relation 服务；并发为 1，每次新建 curl/TCP 连接。正式计时使用 curl `time_total`，包含 DNS、TCP、HTTP 响应传输与实际下游调用，不包含 Docker exec 启动和宿主机 JSON 解析。
- 未停止共享服务、未启动另一套业务栈，没有注入下游延迟或使用 mock 返回值。

## 数据与方法

1. 创建独立的 11 个随机用户、10 对关注/粉丝关系和 320 篇随机笔记读夹具。关系与元数据直接写入 MySQL，正文通过真实 KV API 写入 Cassandra；正文为 512 个 ASCII 字符。数据准备不计时，未把 SQL 夹具当作笔记发布性能证据。
2. 各场景预热 20 次，等待所需容器健康且 CPU 满足脚本声明的稳定条件。预热共 60 次请求，记录为 Round 0，不进入正式统计。
3. 关注列表每次返回 10 个有效用户。正式开始前确认关系 ZSet 和 11 个用户资料 Redis key 已存在；路径仍包含真实的用户服务 Feign 调用，并非仅测 Redis 命令。
4. 正式笔记使用 300 个独立新 ID，开始前确认其详情 Redis key 不存在，且此前未调用详情接口。每篇先测首次详情读取，再立即测同一实例上的第二次读取。当前代码在完整作者和正文可用时同步写入 Caffeine，因此第二次读取走本地详情缓存。
5. 正式测量 3 轮，每轮 100 次关注查询、100 对笔记查询，共 900 次读请求。逐条验证 HTTP 200、业务成功、目标 ID、昵称/作者、完整正文和可见性；不以 HTTP 200 或空结果作为成功样本。
6. 请求间的限速等待在计时之外。平均值使用所有正式样本；P95 使用 nearest-rank。保留每轮结果，不挑选最快轮次。

“首次回源”仅指笔记详情两级缓存未命中。JVM、数据库/操作系统缓存及作者资料已预热，不代表整套系统冷启动。

## 正式读请求结果

| 场景 | 有效样本数 | 平均耗时 | P95 | 无效样本 |
| --- | ---: | ---: | ---: | ---: |
| 关注列表热读，10 条/页 | 300 | 9.212 ms | 12.400 ms | 0 |
| 笔记详情首次回源 | 300 | 10.269 ms | 15.653 ms | 0 |
| 同篇笔记立即命中本地缓存 | 300 | 2.534 ms | 3.943 ms | 0 |

| 轮次 | 关注列表平均 | 首次详情平均 | 缓存详情平均 |
| --- | ---: | ---: | ---: |
| 1 | 10.088 ms | 11.133 ms | 2.807 ms |
| 2 | 9.097 ms | 10.576 ms | 2.532 ms |
| 3 | 8.452 ms | 9.097 ms | 2.262 ms |

缓存命中路径相对首次回源路径的平均耗时下降约 **75.3%**：`(10.269 - 2.534) / 10.269`。简历可写“本地测试中约 10.3 ms → 2.5 ms，降低约 75%”。这是当前同一版本的两种缓存状态对比，不能写成已经测过历史版本改造前后或 CompletableFuture 串行/并行收益。

各轮绝对时延仍有下降，可能包含 JIT、依赖缓存继续预热和共享环境波动。本页报告全部轮次的汇总，不将单次最快响应或最后一轮当作整体结果；不据此推算线上 QPS、承载人数、最大吞吐或持续高并发能力。

```powershell
pwsh -File infra/benchmarks/Invoke-ResumeReadBenchmarks.ps1 -RunId 20261020-rerun01 -Warmups 20 -Rounds 3 -PairsPerRound 100 -FollowingSamplesPerRound 100
```

每次另选未使用的 `RunId`，不超过 17 个 ASCII 字符，只含英文字母、数字和连字符。

脚本用 manifest 核对数据所有权，逐条处理 SQL、Redis key 和 Cassandra UUID，并通过设私密接口使本实例的笔记 Caffeine 缓存失效。清理会验证 Cassandra 围栏及对应 ES 文档消失。合成作者在用户服务的一条 L1 资料缓存没有外部清理接口，按 1 小时 TTL 自然过期；不为清除此条目重启共享服务。

正式脚本已退出 0。最终 `report.json` 为 `eligibleForResume=true`、`cleanup.status=complete`，900 个正式样本全部有效、60 个预热样本未计入结果，错误数为 0，测量期间相关容器重启数为 0。脚本验证自有 SQL、Redis、Cassandra 夹具已移除，对应 ES 文档不存在；笔记本地缓存经真实设私密接口失效。结束后现有应用和配置了健康检查的基础设施仍为 healthy。

独立从原始 JSONL 重算的三个均值和 P95 与脚本报告一致，精确平均值的缓存路径降幅约 75.324%；脚本按毫秒保留三位后计算为 75.32%，正文按约 75% 表达。

# 拾光社区（Shiguang Community）｜后端开发（个人项目）

项目时间请填写实际参与周期；包含本轮改造时，结束时间应覆盖 2026 年 10 月。

**技术栈：** Java 17、Spring Boot 3、Spring Cloud Alibaba、Nacos、Gateway、OpenFeign、MyBatis、MySQL、Redis、RocketMQ、Sa-Token、MinIO、Cassandra、Elasticsearch、Docker Compose

**项目简介：** 拾光社区是一款围绕日常生活、兴趣与经验分享的图文社区，支持内容发布与搜索、点赞收藏、关注互动和评论回复。基于 Spring Cloud Alibaba 微服务架构实现后端，完成服务开发、Docker Compose 本地部署与前后端联调，重点处理缓存更新、消息重复消费及计数偏差问题。

- **网关与认证：** 基于 Gateway、Sa-Token 实现统一登录校验，通过网关和 Feign 拦截器透传用户 ID，避免下游重复解析登录态；接入阿里云短信，利用 Redis 原子占位限制同手机号重复发送，通过 Lua 校验并删除验证码，实现一次性消费，完成短信登录、自动注册及密码登录联调。

- **用户关系：** 实现关注、取关及关注／粉丝列表分页；通过 Lua 原子校验关注状态与人数上限，按用户维度发送 RocketMQ 顺序消息，在 MySQL 事务内维护关注与粉丝双表，以联合唯一索引约束重复关系记录；使用 Redis ZSet 缓存关系列表，本地服务直连测试中（单并发、每页 10 条），缓存命中时接口平均耗时约 **9.2 ms**。

- **笔记服务：** 实现笔记发布、编辑、详情查询、置顶及权限修改，通过 CompletableFuture 并发查询作者资料和正文，结合 Caffeine、Redis 构建详情两级缓存；本地单并发直连测试中，缓存命中的接口平均耗时约 **2.5 ms**，较首次回源的 **10.3 ms** 降低约 **75%**；编辑、删除时持久保存缓存失效任务，经 RocketMQ 广播清理本地缓存并重试 Redis 删除。

- **评论服务：** 实现评论发布、回复、点赞、删除及分页查询；针对消息发送失败和重复消费，将待发送、待处理消息持久化到 MySQL，通过后台重试和事件去重处理异步落库；修复评论缓存缺失项与分页偏移问题，完成发布、查询、删除后的计数变化及缓存失效验证。

- **计数服务：** 针对消息重复处理风险和历史计数偏差，以 MySQL 关注、点赞、收藏等源关系为依据重算相关计数，笔记发布数通过事件 ID 去重；结合行锁、Redis 缓存失效和 XXL-JOB 定时核对发生变更的数据，校正历史偏差，完成关注／取关及评论发布／删除后的计数核对。

- **分布式 ID 服务：** 针对各微服务统一生成主键的需求，接入美团 Leaf，提供号段模式与 Snowflake 模式两种取号能力，并通过 Feign 接口供用户、笔记等业务调用，统一业务主键的生成入口。

以下为准备面试时保留的说明，不必放进简历正文：

- 两个性能指标来自同一份[本地实测报告](../performance/2026-10-20-resume-read-latency.md)。环境为已有本地 Docker 实服务，单并发、服务直连、curl 短连接。每项正式测量 3 轮，每轮 100 次或 100 对，预热样本不计入结果。
- 关注列表是 10 个有效用户的缓存命中页，包含真实用户资料 RPC，平均值并非纯 Redis 操作耗时。
- 笔记的 75% 是同一版本接口“详情首次回源”与“随后的本地缓存命中”两种路径的耗时差异。数据库、JVM、作者资料等已预热，不代表系统冷启动，也不是历史版本改造前后或 CompletableFuture 串并行对比。
- 面试可解释为：首次详情需要查 MySQL 并请求作者与正文；相同详情随后从 Caffeine 返回，所以少走数据库和下游调用。算法为 `(回源平均耗时 - 缓存平均耗时) / 回源平均耗时`。
- 75% 与 9.2 ms 不证明生产容量、线上时延或持续高并发吞吐。Leaf 的 22000+ QPS、4 ms 没有本次实测证据，未沿用。
- 项目跟随「犬小哈」Spring Cloud 实战专栏实现，并在此基础上完成可靠性改造；简历与面试中应如实说明教程来源，不表述为完全原创。
